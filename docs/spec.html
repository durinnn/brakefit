1. 요약

개인투자자는 처분효과·물타기·추격매수 같은 같은 실수를 반복하지만, 정작 자기 거래내역에서 그걸 수치로 본 적이 없다. 매매 브레이크는 증권사에서 내려받은 거래내역 파일 하나로 이 편향 3종을 0~100 으로 점수화하고, 같은 패턴의 주문을 넣으려는 바로 그 순간에 브레이크를 건다 — 개입 근거는 시장 통념이 아니라 그 사람 자신의 과거 거래다. 그리고 "그때 멈췄다면 얼마였나"를 반사실 백테스트로 계산해 숨김 없이 보여준다. 검증 구간이 상승장이라 다섯 페르소나 전부 순손실로 나왔는데, 그 결과를 그대로 띄운다(§7) — 이 서비스가 파는 것은 "브레이크를 걸면 돈을 번다"가 아니라 "당신의 편향이 실제로 얼마짜리였는지 정직하게 계산해준다"이기 때문이다. 판단 경로에는 LLM 이 없다. 지표·룰·백테스트는 전부 결정론적 코드이고, LLM 은 이미 내려진 판정을 사람 말로 옮기는 설명 문구에만 쓰며 그 출력마저 숫자 화이트리스트·금지어 필터를 통과해야 채택된다(§6). 데모는 업로드 → 진단 리포트 → 모의 주문창 개입 팝업 → 반사실 백테스트 순으로 흐른다.

4.1 업로드 /upload

표시 항목

  • (업로드 전) 드래그/클릭 파일 선택 영역 — 선택 시 파일명·용량(KB)으로 갱신, 안내문 2줄("국내 주식 체결 내역만 분석", "업로드 안 해도 데모 페르소나로 전 화면 열람 가능")
  • (업로드 후) 결과 카드 — 거래 건수·기간, 인식된 형식 배지(KB증권 거래내역 / 표준 CSV), 제외된 행 수
  • 확인이 필요한 항목 목록(경고, warnings.length > 0일 때만 노란 테두리 박스)
  • "진단 보기" / "다른 파일 올리기" 버튼

사용자 행동

  1. 파일 선택(accept=".csv,.xlsx,.xls") → 업로드 버튼은 파일 없으면 비활성화
  2. "업로드하고 진단하기" 클릭 → 성공 시 결과 카드로 전환
  3. "진단 보기" → /dashboard로 전체 페이지 이동(클라이언트 라우팅이 아님 — 방금 심은 세션 쿠키를 서버 컴포넌트가 확실히 읽게 하려는 의도적 설계, web/src/app/upload/page.tsx:45-49)
  4. "다른 파일 올리기" → 상태 초기화, 같은 화면 재사용

예외 상태

4.3 모의 주문창 /trade

표시 항목 — 주문 입력 폼(web/src/app/trade/OrderForm.tsx)

  • 종목 select — 내 거래내역에 있는 종목 유니버스(GET /api/universe). 고르면 마지막 종가가 예상 체결가 기본값으로 들어감
  • 매수/매도 토글, 수량 입력, 가격 입력, 총액
  • 하단 큰 버튼 "매수 주문" / "매도 주문" → POST /api/simulate-order 로 판정
  • 합성 데이터 각주(SynthDisclaimer) — 데모 페르소나일 때만

표시 항목 — 개입 모달(판정 결과 shouldIntervene = true 일 때)

  • 주문 요약 — 종목명·코드, 기준 종가(as_of 이하 마지막 종가) 대비 등락률, "매수 N주 · 단가", 총액
    • "전일 대비"가 아니다: 기준 종가는 core/rules/base.reference_close() 가 as_of 당일을 포함해 거꾸로 훑어 찾은 마지막 영업일 종가다. 판정에 쓴 종가와 화면에 뜬 등락률이 같은 함수를 거치게 해서 어긋나지 않게 했다(§6)
  • 위험 게이지(0~100) + 등급(낮음/주의/매우 위험). 개입 팝업이 뜬 상태면 등급은 최소 "주의" — 점수만 보면 낮음 구간인 주문이 많은데(개입 기준이 점수가 아니라 룰 발동이라, §6) 빨간 경고 옆에 초록 "낮음" 게이지가 같이 뜨면 화면 두 곳이 반대 얘기를 하게 된다. 승격은 표시 등급에만 적용하고 점수·판정 자체는 룰이 낸 값 그대로다
  • 기여도 워터폴 — 기준 위험도 → 추격매수 → 물타기 → 처분효과 → 최종 위험 점수, 항목별 근거 문구
  • "과거 패턴 경고" 박스 — 헤드라인 + 유사 사례 건수 + 지배 편향별 평균값(추격매수면 "매수 시점 평균 급등률", 물타기면 "매수 시점 평균 평가손익률", 처분효과면 "사례 평균 손익률") + 설명
  • 대안 제안 목록, "멈추기" / "경고를 무시하고 주문 진행" 버튼
  • shouldIntervene = false 면 모달 없이 통과 카드만 표시

사용자 행동

  • 종목·매수/매도·수량·가격을 입력하고 "매수 주문"/"매도 주문" 클릭 → 판정
  • 개입이면: "멈추기" 클릭 → "주문을 멈췄습니다" 확인 화면(로컬 상태 전환만)
  • "경고를 무시하고 주문 진행" 클릭 → 2단계 확인 박스("정말 이 주문을 진행하시겠습니까?") → "그래도 매수" 클릭 → "경고를 무시하고 주문이 접수되었습니다" 표시
  • 개입이 아니면 모달 없이 통과 카드로 넘어감
  • 참고: 위 "멈추기"/"그래도 매수" 결정은 클라이언트 로컬 상태일 뿐 서버에 남지 않는다. 예전엔 문구가 "다음 진단에 반영됩니다"/"24시간 뒤 알려드릴게요"로 미구현 기능을 약속했는데, 실제 동작에 맞춰 정정함

4.4 백테스트 /backtest

이 화면에 뜨는 수치는 §7 결과표와 같은 값이다(같은 GET /api/backtest 응답). §7 은 2026-09-05 A 확정 — 인용 제한 없음. 다만 다섯 페르소나 전부 순손실이라 화면 NET 카드가 빨강으로 뜬다. 그 자체가 결론이라는 게 §7 의 입장이니 숨기지 않는다.

표시 항목

  • 기간·개입 대상 건수
  • NET 카드 — 순수익 금액·비율. 부호에 따라 색상이 갈림(양수=safe 초록, 음수=risk 빨강 — 지난 버그 수정 반영됨)
  • 개입 건수 · 개입 적중률
  • 회피한 손실 / 놓친 이익 막대바 2개 + 계산식("회피 손실 − 놓친 이익 = 순효과")
  • 주요 개입 사례 목록 — 날짜·종목명·편향 종류·impact 금액
  • 합성 데이터 각주(SynthDisclaimer) — 데모 페르소나일 때만

사용자 행동

5. 편향 정의와 점수 산식

각 편향: 정의 1줄 → 거래내역에서 잡는 방법 → 점수 0~100 산식 → 근거(evidence) 예시.

등급(안정/주의/위험)은 종합 점수에만 붙는다 — 지표별 등급은 없다. 컷은 api/service.py GRADE_THRESHOLDS: 종합 < 40 안정 · < 70 주의 · ≥ 70 위험. 개별 지표는 점수와 백분위(§5.4)만 표시한다.

5.1 처분효과 (disposition)

  • 정의: 오른 종목은 서둘러 팔고(익절), 내린 종목은 계속 버티는(손절 회피) 경향. Odean(1998) PGR/PLR 그대로 사용.
  • 잡는 방법: 청산 episode 는 realized_pnl 부호로, 미청산 episode 는 timeline 최신 스냅샷의 unrealized_pnl 부호로 이익/손실 건을 가른다 (3%/-3% 같은 문턱 없음 — 부호만 봄, 문턱을 두면 그 구간 실현손익 부호가 랜덤에 가까워져 신호가 희석됨).
    • PGR = 실현이익 건수 / (실현이익 건수 + 미실현이익 건수)
    • PLR = 실현손실 건수 / (실현손실 건수 + 미실현손실 건수)
  • 산식: raw = PGR − PLR (이론상 [-1, 1]) → score = (raw + 1) / 2 × 100
  • evidence: 가장 빨리 판 이익실현 건 1개 + 가장 오래 버틴 손실(미실현 포함) 건 1개

5.2 물타기 (averaging_down)

  • 정의: 이미 평가손실 상태인 종목에 추가매수하는 경향. 진입 매수 자체는 물타기가 아니다 — 진입 이후 추가매수만 센다.
  • 잡는 방법: BUY 건을 (ticker, traded_at)으로 해당 episode 구간에 역매칭 → 진입일 매수 제외 → 매수 당일 timeline 스냅샷의 unrealized_pnl < 0 인 건만 카운트.
    • 최초 구현부터 −5% 문턱 없이 손실 여부(< 0)만 봄 — README가 "−5% 이하"로 잘못 적혀 있던 걸 코드 기준으로 정정함(README §5).
  • 산식: raw = 손실 상태 추가매수 건수 / 전체 매수 건수 → score = raw × 100
    • 진입 매수는 분자에서만 빠지고 분모(전체 매수 건수)에는 남는다. PR 26 에서 §5.3 분모가 전체 매수 건수로 복원되면서 두 지표의 분모 정의가 일치한다("이 사람의 매수 중 몇 %가 이 패턴이었나").
  • evidence: 평가손실 상태에서 추가매수한 건 나열

5.3 추격매수 (chasing)

  • 정의: 이미 오른 종목에 더 오를 걸 기대하고 뒤늦게 따라 들어가는 경향.
  • 잡는 방법: 이미 보유 중인 종목에 대한 같은 episode 내 추가매수 중, 전일 종가 대비 +5% 이상 급등한 가격에 매수한 건을 카운트.
  • 산식: raw = 급등 후 매수 건수 / 전체 매수 건수 → score = raw × 100
    • 분모는 전체 매수 건수다 — 판정 가능 건수만 쓰던 초기 구현을 리더 결정으로 되돌렸다(PR 26, core/metrics/chasing.py). 보유 이력이 없어 전일 종가를 몰라 판정할 수 없는 매수는 분모에 남되 분자에 0으로 들어간다(= "추격 아님" 쪽으로 보수적으로 기움, 편향 점수를 과대평가하지 않는 방향).
    • 판정 가능 건수만 분모로 쓰던 동안에는 판정 가능 건이 seed당 0~8건까지 떨어져 점수가 0~100을 오갔고, 대조군이 100점을 받아 추격형과 구분되지 않았다. 복원 후 5종이 정상 정렬됐다(§5.4 표).
  • evidence: 급등 후 매수 건 나열 (급등률 %, 매수 시점 기준 — 그 이후 실제 수익률 아님)
  • ⚠ 스키마 한계(지표에만 남아 있음): 신규 진입 종목의 "당일 급등 후 추격매수"는 같은 episode 안에 비교할 전일 종가가 없어 판정 불가. timeline.close 는 포지션을 들고 있는 동안에만 존재하는 값이라 그렇다.
    • 브레이크 룰(§6)에는 이 한계가 없다 — PR 27 에서 룰이 timeline 대신 시세 캐시를 보게 바뀌어 미보유 종목도 판정한다. 지표를 같은 방식으로 옮기는 건 점수 정의와 백분위 기준선을 다시 잡아야 해서 v1 범위 밖(로드맵 항목).

기준 종가 (PR 27, core/rules/base.reference_close)

  • 정의: as_of 이하(당일 포함) 마지막 영업일 종가. 출처는 timeline 이 아니라 시세 캐시(core/synth/prices.get_daily_close, docs/schema.md §5). 영업일이 없으면 최대 14일 거꾸로 훑는다(연휴 대응).
  • as_of 당일을 포함하는 이유: 실제 호출 경로에서 as_of 는 이미 주문 시점보다 앞선 날이라 그날 종가는 주문자가 이미 아는 값이다. 개입 판정은 as_of = 마지막 거래일(데모 DEMO_AS_OF=2026-08-18), 백테스트는 cutoff = 매수일 − 1일. 당일을 빼면 오히려 §5.3 지표의 T−1 기준과 하루 어긋나고, /api/universe 의 lastClose 와 팝업 changeRate 가 서로 다른 종가를 가리켰다.
  • 룩어헤드 경계는 이 함수 한 곳뿐이다 — 조회 구간의 끝을 as_of 로 못박아 as_of 초과 종가는 함수 안으로 들어오지 못한다. data/cache/prices 는 as_of 보다 뒤 날짜까지 갖고 있어서, 이 경계가 없으면 조용히 미래를 쓴다.
  • 룰·표시용 등락률·주문 폼 기본가가 전부 이 함수 하나를 거친다 — 화면에 뜬 기준 종가와 판정에 쓴 기준 종가가 갈라지지 않게.

  • 시세를 못 구하면(미캐시·네트워크·lookback 안에 영업일 없음) 발동하지 않고 RuleContribution.warnings 에 사유를 남긴다. triggered=False 만 보면 "급등 아님"과 "판정 못 함"이 구분되지 않기 때문(AGENTS.md "예외는 삼키지 않는다").

  • risk_score = 세 룰의 기여 점수 합 (0~100). 룰이 하나라도 발동(triggered)했거나 risk_score ≥ INTERVENE_THRESHOLD(50) 이면 개입 팝업 표시 (core/rules/engine.py)

    • 근거: core/backtest 는 룰별 triggered 로 개입 주문을 센다. 팝업만 점수 임계값을 쓰면 "백테스트가 센 주문"과 "팝업이 뜨는 주문"이 어긋난다 — 판정 기준을 triggered 로 통일함
    • riskLevel(낮음/주의/매우 위험)은 점수 강도를 따로 표현하는 표시용 값이다. 컷은 api/service.py RISK_LEVEL_THRESHOLDS(30/50)이되, 개입이면 최소 "주의"(MEDIUM)로 올린다 — 개입 기준이 점수에서 triggered 로 바뀐 뒤 "빨간 경고 팝업 + 초록 낮음 게이지" 조합이 실제로 나왔기 때문이다(실측 24.35점). "매우 위험"(HIGH)은 점수 ≥ 50 이라는 원래 의미를 유지한다. 개입 여부를 riskLevel 로 되짚으면 안 된다(§4.3)
  • dominantKey — 발동한 룰 중 기여 점수가 가장 큰 편향의 키(chasing/averaging_down/disposition). 개입일 때만 채워지고, 화면의 "과거 패턴 경고" 박스가 어떤 편향의 평균값을 보여줄지 고르는 근거다. 개입이 아니면 null
  • 세 룰 다 "과거 편향 점수가 높을수록 이번 주문의 위험 기여가 커진다"는 동일 구조 — 전역 가중치가 아니라 개인 실증(자기 과거 점수)에 근거를 묶어 "가중치 근거가 뭐냐" 공격을 무력화하는 설계(README §4.2)

stale 타임라인 버그 수정 (PR 26·27)

세 룰이 전부 timeline 을 종목만으로 걸러 마지막 행을 집고 있었다. 그래서 몇 달 전 청산된 옛 에피소드의 마지막 행이 "현재 상태"로 둔갑했다.

  • 물타기·처분효과: 열린 episode(episodes.is_open, as_of 기준)로 스코프를 제한하고, 열린 게 없으면 미판정. 실측 사례 — 데모 페르소나 5종 전부가 삼성전자 SELL 에서 처분효과 개입을 받았는데 그중 셋은 DEMO_AS_OF 에 삼성전자를 보유하고 있지도 않았다. 안 들고 있는 종목은 팔 수 없으니 처분효과 대상이 아니다.
  • 추격매수: 같은 방식으로 "열린 에피소드 안에서만" 조건을 걸었더니 이번엔 미보유 종목을 영원히 판정 못 하게 됐다 — 정작 추격매수의 교과서적 형태가 "안 갖고 있던 종목이 급등하니까 따라 들어가는 것"인데도. 그래서 timeline 을 버리고 위의 기준 종가(시세 캐시)로 옮겼다. 보유 여부와 무관하게 판정 가능하고 stale 이 구조적으로 불가능하다.
  • 처분효과의 평가손익도 timeline.unrealized_pnl(그 행 날짜의 종가 기준) 대신 기준 종가 − 평단 으로 다시 계산한다. 열린 에피소드로 스코핑해도 "마지막 행 날짜 == as_of" 가 보장되지 않아서(거래정지·캘린더 결측) 기준일이 어긋났다. 시세를 못 구하면 timeline 값으로 물러서되 사유를 warnings 에 남긴다.
  • 회귀 테스트 동반(tests/, 전체 219개 통과 — 부록 C)

  • 룩어헤드: 판정은 주문 시점, 평가만 사후 가격.

아래 표는 로컬 GET /api/backtest 를 페르소나 5종에 전부 호출해 받은 실측값이다 (2026-09-05, §6 의 기준 종가·stale timeline 수정이 반영된 코드). 인용 제한 없음 — 단, 반드시 아래 각주 (a)(b)(c) 와 함께 인용한다.

헤드라인

검증 구간(2025.11~2026.08 KRX 상승장)에서는 개입이 순손실이다. 5개 페르소나 전부 netBenefit 이 음수로 나왔다.

이걸 감추거나 유리한 기간을 골라 다시 돌리지 않는다. 편향 차단이 항상 수익을 만드는 게 아니라는 결과를 그대로 보여주는 것 자체가 백테스트 기능의 목적이다. 이 서비스가 파는 것은 "브레이크를 걸면 돈을 번다"가 아니라 "당신의 편향이 실제로 얼마짜리였는지 반사실로 계산해 보여준다"이고, 그 계산기가 정직하게 작동한다는 증거가 이 음수다.

각주 — 이 표를 인용할 때 반드시 함께 붙인다

(a) 기간 의존성. 검증 구간은 커밋된 시세 캐시(data/cache/prices, 8종목 일봉)가 덮는 2025.11.03~2026.09.03 이고, 페르소나별 거래 기간은 그 안의 부분구간이다(표의 "기간" 컬럼). 이 구간은 KRX 가 대체로 상승한 국면이다. 물타기· 추격매수 룰은 매수를 막는 방향이라, 상승장에서는 "막았어도 어차피 올랐을" 확률이 구조적으로 높아 놓친 이익이 커진다. 즉 이 표의 음수는 브레이크 로직의 결함이 아니라 결과가 시장 국면에 의존한다는 사실을 보여준다. 하락장·횡보장 구간을 추가 검증하지 않는 한, 이 수치를 "브레이크가 도움이 된다/안 된다"는 일반적 근거로 제시하면 안 된다.

(b) 합성 페르소나 결과다 — 실사용자 분포가 아니다. 거래는 core/synth 가 Monte Carlo 로 생성했고 시세만 pykrx 실데이터다(AGENTS.md 규칙 6). 페르소나 파라미터가 곧 "편향의 세기"라, 실제 개인투자자 모집단에서 이 크기의 효과가 나온다는 뜻이 전혀 아니다.

(c) 처분효과(SELL)는 포함되지 않았다. v1 백테스트 범위는 매수를 막는 룰 2종 (물타기·추격매수)뿐이다. "팔지 말았어야 했다"의 반사실은 "그 물량을 언제까지 들고 있었을 것인가"를 가정해야 정의되는데, 그 가정이 결과를 좌우해버려 제외했다 (근거: core/backtest/backtest.py 모듈 docstring). 따라서 처분효과형 페르소나의 −77,000원은 그 페르소나가 부수적으로 낸 BUY 편향만 잡은 값이다.

데모 시연 각도: 백테스트 탭을 감추지 않는다. 다섯 페르소나 전부 NET 카드가 빨강으로 뜨는 걸 그대로 보여주고, 그 자리에서 위 헤드라인을 말한다 — "상승장에서는 이렇게 나옵니다, 그리고 그게 나온다는 게 이 화면이 정직하다는 뜻입니다." 유리한 기간을 찾아 재검증하는 선택지는 버린다(체리피킹이라 심사에서 더 크게 깨진다).

10. 한계와 다음 단계

데이터·범위

  • 국내주식 전용, KB증권 화면 3종만. 해외주식은 KRX 종목코드가 없고 통화가 달라 파싱은 되지만 분석 파이프라인에 태우지 못한다(§8). 다른 증권사는 YAML 매핑을 추가해야 한다.
  • 실사용자 데이터로 검증되지 않았다. 모든 수치는 합성 페르소나(core/synth, Monte Carlo + pykrx 실시세) 기준이고 실제 개인투자자 모집단의 분포가 아니다(§7 각주 b).
  • 세션은 비영속이다. 업로드한 거래내역은 서버 메모리에만 있고(50개 LRU), 재배포·콜드스타트·LRU 밀림 어느 쪽이든 사라져 이후 요청은 404 → 데모 페르소나 폴백이 된다. 디스크 저장을 안 하는 건 개인정보를 안 남기려는 의도적 선택이지만, 그 대가로 "어제 올린 내역 다시 보기"가 불가능하다.

분석 방법

  • 백테스트 결과가 기간에 의존한다. 검증 구간(2025.11~2026.08)이 KRX 상승장이라 매수를 막는 룰은 구조적으로 불리하다 — 다섯 페르소나 전부 순손실이다(§7 각주 a). 하락장·횡보장을 추가 검증하지 않는 한 이 표를 "브레이크가 도움이 된다/안 된다"의 일반 근거로 쓸 수 없다.
  • 처분효과 백테스트가 없다. "팔지 말았어야 했다"의 반사실은 "언제까지 들고 있었을 것인가"라는 가정이 결과를 좌우해서 v1 에서 뺐다(§7 각주 c). 즉 3종 중 1종은 개입은 하되 금액으로 증명하지 못한다.
  • 백분위는 참고용이다. 기준선이 합성 페르소나 5종 × seed 4개 = 20 표본이라 해상도가 5% 단위다(§5.4).
  • 종합 점수 가중치 40/35/25 의 근거가 약하다. 룰의 MAX_CONTRIBUTION 을 그대로 재사용한 값이지 실증으로 고른 값이 아니다.
  • 지표 쪽 chasing 은 신규 진입 매수를 판정하지 못한다(§5.3). 룰(§6)은 시세 캐시로 옮겨 해결했지만, 지표를 같은 방식으로 바꾸면 점수 정의와 백분위 기준선을 다시 잡아야 해서 v1 범위 밖이다.
  • 편향 정의 자체가 근사다. 처분효과는 Odean(1998) PGR/PLR 을 문턱 없이 부호로만 갈랐고, 물타기·추격매수는 문턱(손실 여부·+5%)과 분모(전체 매수 건수)를 이 서비스가 정한 값이다. 정의를 바꾸면 점수가 바뀐다.

운영

  • 인증이 없고 CORS 가 전면 개방이라 데모 범위를 벗어난 배포에는 그대로 쓸 수 없다(§9).
  • LLM 문구는 실패 시 템플릿으로 폴백되므로, 네트워크·키 상태에 따라 같은 주문에서 다른 문구가 나올 수 있다(판정 결과는 결정론이라 바뀌지 않는다, §6).
